# ALOX Vision (Python) for the machine PCs: build and installation

This folder packages the integrated application (`alox`) for the Windows PCs of the machines, **side by side with the
LabVIEW application** (migration plan, phase 12): the LabVIEW installation, its folders and its settings are never
touched, only one of the two applications runs at a time, and uninstalling the Python application is the rollback.

| File | What it is |
|---|---|
| `alox.spec` | PyInstaller spec: the one-folder application `AloxVisionPy\` |
| `entry\` | The entry scripts of the executables (`alox.exe`, `alox-ui.exe`; the check-tool ones are generated by the spec) |
| `alox.iss` | Inno Setup script: the installer `AloxVisionPy-<version>-setup.exe` |
| `build.ps1` | Builds both in a clean venv |
| `alox_setup.ini.example` | Template of the machine's `alox_setup.ini` (installed next to `alox.exe`) |
| `after_install.txt` | The checklist shown at the end of the installation |

The folder `AloxVisionPy\` holds `alox.exe` (console: the server / headless application, `--check`, `--ui`),
`alox-ui.exe` (windowed: the same with `--ui`), the check tools `z_stage_check.exe`, `xy_stage_check.exe`,
`wl_check.exe`, `camera_check.exe`, `thermal_check.exe`, `af_latency_check.exe` (console), `_internal\` (Python and the
libraries: NumPy, SciPy, Pillow, OpenCV, PySide6, pyserial, FastAPI / uvicorn / websockets, cryptography, Harvesters /
genicam) and `alox_setup.ini.example`. The executables take the same options as `alox` and `py -3 tools\<tool>.py`
(see the main [README](../../README.md)).

## Building

Prerequisites on the build PC (Windows 10/11 x64, not a machine PC):

- **Python 3.13 x64** from python.org, with the `py` launcher (or give `-Python C:\...\python.exe`);
- **Inno Setup 6.3 or later** (https://jrsoftware.org/isdl.php); without it only the folder is built;
- network access to pypi.org; Git (optional: the commit is written into the version resource and the check-tool
  reports).

From the repository folder, in PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File packaging\windows\build.ps1
```

1. creates `packaging\windows\build\venv` (clean) and installs `.[stage,api,ui,vision,licence]`, `pyinstaller` and
   `harvesters`;
2. runs PyInstaller with `alox.spec` → `packaging\windows\dist\AloxVisionPy\`;
3. smoke test: `alox.exe --version`, `alox.exe --simulate --check`;
4. runs `ISCC.exe alox.iss` → `packaging\windows\dist\installer\AloxVisionPy-<version>-setup.exe`.

Options: `-LicencePublicKeyFile <licence_public_key.txt>` ships the licence public key (never the private key),
`-SkipInstaller`, `-SkipSmokeTest`, `-KeepVenv` (faster rebuild). `build\` and `dist\` are ignored by git.

The spec takes `alox` / `aloxcam` from `src\` and the tools from `tools\`; it stops when a dependency is missing
(`ALOX_PYI_ALLOW_MISSING=1` builds anyway, for tests). On Linux the same spec builds the same folder without `.exe`
(how the bundle is checked without Windows):

```sh
pyinstaller --noconfirm --distpath /tmp/pyi/dist --workpath /tmp/pyi/build packaging/windows/alox.spec
/tmp/pyi/dist/AloxVisionPy/alox --simulate --check
QT_QPA_PLATFORM=offscreen /tmp/pyi/dist/AloxVisionPy/alox-ui --demo --screenshot /tmp/pyi/window.png
```

## Installing on a machine, next to LabVIEW

Run `AloxVisionPy-<version>-setup.exe` as administrator. It installs into `C:\Program Files\Aloxtec\AloxVisionPy`,
its own folder (LabVIEW's camera server is in `C:\Program Files\alox`), with the Start-menu group
**Alox Vision (Python)**: *Alox Vision*, *Alox Vision (simulation demo)*, *Alox Vision server (console)* and
*Check tools\\…* (each opens a Command Prompt in the installation folder with the tool's help). It writes no registry
key, environment variable or service of its own besides the uninstall entry.

The page **LabVIEW installation (read only)** asks for the folder of the LabVIEW Vision Core application (the folder of
its `.exe`); setup then copies from it, only when they are not already in the Python folder:

| Copied from LabVIEW | To | Why |
|---|---|---|
| `translations\*.lang` | `<install>\translations\` | the texts of the window and of the error codes (`alox_en.lang`, `system_en.lang`, …) |
| `alox_default.ini` | `<install>\alox_default.ini` | the defaults from which `<settings>\alox.ini` is created at the first start |

Leave the field empty to copy them by hand later (administrator rights). **Never the passwords**: neither the build,
nor the installer, nor a report carries `alox.ini` or a `[user.password]` section; the Python application reads the
passwords from the `alox.ini` of its own settings folder on the machine.

What else goes where (`<install>` = `C:\Program Files\Aloxtec\AloxVisionPy`, the `<exe>` folder of the application):

- **`<install>\alox_setup.ini`**, the machine's `[folders]`: setup never writes it and the uninstaller never removes
  it, so an update keeps it. Copy `alox_setup.ini.example` to `alox_setup.ini` and edit it. The template uses separate
  folders (`D:\alox-py\…`) so that the test sessions leave LabVIEW's settings, recipes and data untouched; copy the
  machine's `alox.ini` (from LabVIEW's settings folder, a copy) and the recipes to test into them. To share LabVIEW's
  folders instead, copy LabVIEW's `alox_setup.ini`; the Python application then writes there (settings, recipes,
  data, logs). Without `alox_setup.ini` the LabVIEW defaults `D:\alox\…` apply.
- **IDS GenTL producer**: installed by IDS peak (with the "Kernel (GEVK)" GigE Vision transport layer), which sets
  `GENICAM_GENTL64_PATH`; the application scans it. To load one producer only, add
  `--genicam-producer "C:\Program Files\IDS\ids_peak\…\ids_gevgentlk.cti"` to the shortcut's target
  (`dir /s /b "C:\Program Files\IDS\*.cti"` shows the path).
- **Licence** (only when `alox.ini [general] licence_BOOL = TRUE`, off by default): `<install>\licence_public_key.txt`
  (from the build, `-LicencePublicKeyFile`) and the machine's `<install>\licence.alox`, issued for this PC with
  `tools\licence_generator.py` and copied by hand.
- Per user: the log of `alox-ui.exe` in `%LOCALAPPDATA%\Aloxtec\AloxVisionPy\logs`, the simulation demo in
  `%LOCALAPPDATA%\Aloxtec\AloxVisionPy\demo` (delete it to start the demo afresh), the check-tool reports in
  `Documents\AloxVisionPy\reports` (or the current folder when started elsewhere, or `--out`). `alox.exe` logs to its
  console; `--log-dir <folder>` adds daily files.

## First start on the machine (a side-by-side test session)

LabVIEW **stopped** for every step (the stages, cameras and serial ports are opened exclusively); the simulation demo
needs no hardware and no network port and can be started at any time.

1. **Check tools** (Start menu > Alox Vision (Python) > Check tools), each first as a rehearsal, then on the hardware,
   e.g. `z_stage_check.exe --fake --motion --yes`, then `z_stage_check.exe --alox-ini D:\alox\settings\alox.ini`
   (read only); likewise `xy_stage_check`, `wl_check`, `camera_check` (`--list` first), `thermal_check`,
   `af_latency_check`. The procedures are in the main README (sections "Check the …"). Send back the reports.
2. **`alox.exe --check --alox-ini <settings>\alox.ini`** in the Command Prompt (`<settings>` of `alox_setup.ini`):
   opens the devices with the machine's settings, prints their status as JSON, exit code 0 when all are ready.
3. **`alox.exe --ui`** (or the *Alox Vision* shortcut): the whole application with the operator window; the supervisor
   API on ports 8002 (REST) and 6123 (websocket), as LabVIEW.
4. Close it, start LabVIEW again.

## Updating and rolling back

- **Update**: run the new setup; the bundle (`_internal\` included) is replaced, `alox_setup.ini`, `alox_default.ini`,
  `translations\` and the licence files are kept.
- **Rollback**: uninstall *ALOX Vision (Python)* (Settings > Apps). LabVIEW was never changed and starts as before. The
  uninstaller leaves `alox_setup.ini`, `alox_default.ini`, the licence files, the Python data folders (`D:\alox-py\…`),
  the logs, the demo and the reports; delete them by hand if they are not wanted.
